# 1.7 实验档案：为「更少资源找出最优解」做过的尝试

1.7.0 的搜索部分**没有新默认值**。这一版收录的是一整条实验线：为了回答「能不能用更少的节点
找到同样好的线」，我们做了 9 轮测量、4 次夹具迭代、写了 11 道门禁（S283–S293），其中多数
假设被数据否掉。本文把每一轮的夹具、方法、数字和结论都留档，方便以后复盘，也方便任何人
沿着同样的命令重跑。

被否掉的假设和成立的假设一样有价值：这份档案记录的重点不是「我们加了什么」，而是
「我们凭什么确定加什么、不加什么」。

| --- | --- | --- | --- |

| 2 | S283（三断言） | 同样的最好线，谁更早到达？ | `bestAt` 指标；无变体更早；发现基线本身到 96% 预算才收敛 |

| 5 | S287–S289 | 矩阵结果异常，是不是键/早停有正确性缺口？ | 药水与遗物计数不在键里；零成本早停实测丢 ~12k 分 |

## 1. 目标与判定标准

1.7.0 的目标是「更少资源找出最优解」。判定标准从一开始就很严：

- **最好线不变**（同一预算下 final score 相同，且步骤内容相同）；
- **资源明显更少**（节点数或 `bestAt` 显著下降）；
- 只有同时满足、且跨 seed 稳定成立的开关，才允许进入默认。

第一轮之后又补了一条：**「最优」必须有一个明确的预算参照**。第 3 轮证明 20k 节点下的
「最优」只是局部最优，因此后续所有比较都写明 cap 与 seed，并且不再声称「不损失最优性」。

## 2. 方法与仪器

- 搜索引擎：`Solver.Session(root, beam=24, maxLayer=96, budgetMs, maxNodes, bandOffset=0)`，
  每一步都是引擎真实执行后得到的 `World`。
- 夹具：`Synthetic` 在真实游戏里搭出战斗（真实牌、真实怪物、真实 RNG），同一夹具+seed 只
  构建一次，所有变体共享同一个 `World.captureLive()` 根。
- 变体（第一轮定义，后续复用）：

| 变体 | 内容 |
| --- | --- |
| V0 | 基线 |
| V1 | RNG 计数器并入搜索键 |
| V2 | dominance 剪枝 |
| V3 | turnPlan 关闭 |
| V4 | targetFocus 关闭 |
| V5 | diversity（按动作类保底的 beam 择优）关闭 |

- 判等：`planSameAsV0` 为同一运行、同一夹具+seed 的最好线步骤 digest 是否与 V0 逐字节相同。
  **`plan=` 哈希含每进程重建的卡牌 UUID，跨进程不可比**，所以所有跨运行比较只比
  score / nodes / steps / bestAt / proven。
- 每格都记录 `nodes / transpositions / merged / skipped / dominated / ms / bestScore /
  status`；后续轮次增加 `bestAt / bestUpd / curve / proven / steps`。
- 每个夹具×seed 的预期数字都写成门禁断言（不是「跑完看一眼」）；每次实测后恢复官方 jar
  并复核哈希。

## 3. 第 1 轮：S283 变体矩阵（F1–F3）

夹具（maxHealth 80，seeds 9301–9303）：

| 夹具 | 怪物 | 牌组 |
| --- | --- | --- |
| F1 | JawWorm | 5×Strike_R / 4×Defend_R / Bash |
| F2 | Cultist + JawWorm | 4×Strike_R / 4×Defend_R / Bash / Shrug It Off |
| F3 | LouseNormal + LouseDefensive | 3×Strike_R / 2×Defend_R / Bash / 2×Pommel Strike / Shrug It Off / Battle Trance |

54 格（3 夹具 × 3 seed × V0–V5），20k 节点上限。门禁 S283 在聚焦与全 mod 两种环境各
**108/108**（54 格 × 2 条断言），节点/分数/合并数逐格相同 ⇒ 搜索结果对 mod 加载不敏感。

结论：

1. **没有任何「最好线相同、节点明显更少」的变体**。唯一的「同线且节点少」是 F1/9301 V5
   （289→285，−1.4%），幅度在噪声尺度，同一变体在其余 seed 全是反例。
2. V1 改变合并数 ≤1%，最好线与分数全同；V2 dominance 基本是空操作（唯一差异
   F2/9302 `dominated=4`）；V3 turnPlanOff 连节点数都完全相同——在这些夹具上没触发。
3. V4/V5 会改变最好线，F2 三个 seed 两降一升、方向不一致，不能作为候选。
4. **夹具本身不合格**：F1/F3 在 214–493 节点自然收敛；F2 每格都撞满 20k，节点数按构造相等，
   把「少用节点」的任何差异都截掉了。第一轮只能回答「线是否变」，不能回答「省不省节点」。

## 4. 第 2 轮：nodes-to-best（S283 三断言）

为回答「找到同样最优要多少节点」，`Solver` 在最好分每次严格提升时记录已生成节点序号：
`bestAt` = 最终最好分首次达到的节点序号，`bestUpd` = 提升次数。默认关，仅测量钩子。
S283 加三重断言（产出行 / 有最好线 / bestAt 合法且与 bestUpd 一致），**162/162 通过**。

结论：

1. 仍然没有「同线同分、明显更早到达」的变体。同线同分格子里唯一变化是 F2/9303 V1：
   bestAt 8848→8781（早 67 个节点，0.75%），其余 8 个 seed 与 V0 完全相同。
2. **最重要的发现不在变体而在基线**：F2/9302 直到第 19,199 个节点（预算的 96%）才达到最终
   最好分。20k 预算可能就是截断线，当前数据无法证明 20k 的结果是最优。
3. 同时也否掉了一个后来被反复提起的优化：一个通用的「连续若干层无改进就停」会在 F2/9302
   上砍掉最终最好线（最后改进发生在搜索末尾）。

## 5. 第 3 轮：预算敏感性（S285）

F2 × 3 seed × V0，20k / 40k / 80k。门禁 **30/30**，20k 列与第 2 轮逐位一致（回归控制）。

| seed | cap | nodes | bestAt | bestScore |
| --- | --- | --- | --- | --- |
| 9301 | 20000 | 20000 | 2400 | 10,013,559 |
| 9301 | 40000 | 40000 | 2400 | 10,013,559 |
| 9301 | 80000 | 80000 | **72,343** | **10,019,556** |
| 9302 | 20000 | 20000 | 19,199 | 10,015,001 |
| 9302 | 40000 | 40000 | 19,199 | 10,015,001 |
| 9302 | 80000 | 54,908（穷尽） | 19,199 | 10,015,001 |
| 9303 | 20000 | 20000 | 8,848 | 10,001,248 |
| 9303 | 40000 | 40000 | 24,635 | 10,001,249 |
| 9303 | 80000 | 69,920 | 47,881 | 10,003,245 |

结论：**20k 不是最优**。9301 在 80k 的第 72,343 个节点找到 +5,997 分的新线；9303 在 40k/80k
各改进一次，线都变了；只有 9302 的 20k 结果等于 80k 结果。预算不是浪费——在 9301/9303 上
它直接换来了更好的答案。此前「V1–V5 同线/改线」的结论仍成立，但只能限定在该预算意义上。

## 6. 第 4 轮：分数-节点曲线（S286）

F2 × 3 seed × V0–V5，80k 上限，记录 100/250/500/1k/2k/4k/8k/16k/32k/64k/128k 节点处的当前
最好分。门禁 **90/90**（曲线单调、末点不高于最终分、每格成行）。18 格代表值：

| seed | V0 终分 / bestAt | V4 终分 / bestAt | V5 终分 / bestAt |
| --- | --- | --- | --- |
| 9301 | 10,019,556 / 72,343 | 9,991,569 / 14,825（+80k 前耗尽） | 10,019,558 / 70,437 |
| 9302 | 10,015,001 / 19,199 | 10,007,014 / 28,298 | 9,980,999 / 23,438 |
| 9303 | 10,003,245 / 47,881 | 10,021,245 / 34,727 | 10,017,247 / 59,347 |

结论：

1. **V1/V2/V3 与 V0 不是「接近」，而是逐点相同**：所有阈值、最终分数、最终线完全一致
   （V1 仅总节点少 67–259 个，属合并差异，不改变曲线）。
2. **V4 targetFocusOff 是赌博**：9303 上 +18,000 分且在 4k 节点就拿到，但 9301 −12,798、
   9302 −7,987，三个 seed 方向相反。
3. **V5 diversityOff 同样不稳定**：9302 −13,400，9303 +14,002，9301 基本持平。
4. 曲线形状：V0 的大部分质量在 2k–4k 节点内已经拿到；9301 的 +6,000 与 9303 的 +329 都在
   32k 之后。**没有任何开关让「同样的最终线」提前到达**——1.7.0 没有可采用的默认改动。
5. 剩下的方向是「改变保留什么节点」，而不是调现有开关。这成了 1.8 的实验方向。

## 7. 第 5 轮：正确性缺口（S287–S289）

矩阵结果里有一批「怎么都测不出差别」的开关。为了排除仪器问题，我们直接审计了搜索键与
早停判据，结果是三个真问题：

### 7.1 S287：搜索键看不见药水与遗物计数（4/4）

同一块棋盘的两个克隆，只改一处，比较 `Digest.stable(ofCurrent())`：

| 改动 | 两个摘要 |
| --- | --- |
| 药水槽 0：`Potion Slot` → `Fire Potion` | 都是 203 字符，逐字节相同 |
| Nunchaku `counter` 0 → 7 | 都是 212 字符，逐字节相同 |

后果：一条「用掉药水」的线和一条「没用药水」的线落到同一块棋盘时会被当作同一节点，
仍持有药水的那条可能被永久丢弃。F1–F3 没有药水，所以矩阵从未触发；真实对局会。

### 7.2 S288：失败 rollout 不再排到最前（6/6）

`rerankByRollout` 用 `rb - ra` 比较，而失败值是 `Integer.MIN_VALUE`，差值溢出会让失败节点
抢到 beam 槽位。改为显式规则：失败值一律最后。rollout 默认关，正式行为零变化。

### 7.3 S289：零成本早停实测丢约 12,000 分（6/6）

夹具：4×Strike_R + **Feed** + 3×Defend_R，单只 LouseNormal，80 HP。同一块棋盘跑两次，
唯一区别是早停开关：

| seed | 早停开：nodes / score | 早停关：nodes / score | 差值 |
| --- | --- | --- | --- |
| 9301 | 14 / 10,023,597 | 30,000 / 10,035,593 | +11,996 |
| 9302 | 5 / 10,023,038 | 30,000 / 10,035,032 | +12,994 |
| 9303 | 21 / 10,023,277 | 26,409 / 10,035,271 | +11,994 |

原因可证也可测：早停判据只用 `n20==0 && n21==0`（掉血、药水），而赢线分数还含
`healPoints(postHeal)`、`lootPoints(loot)`、`GrowthBook.credit(...)`。把成长预算钉零再跑，
分数各降 6,001——**成长约占一半，战后治疗占另一半**，两项都不在判据里。三个 seed 都在
0.1% 预算内停下，不是偶然。

### 7.4 结论

前几轮「开关无效」不是机制坏了，而是夹具太简单；但搜索里确实存在一个会主动丢分的早停，
它与四个开关无关。这比「省节点」更值得先修。修法必须默认不变：不猜分数上限，只加 opt-in
开关（见第 6 轮）。

## 8. 第 6 轮：两枚默认不变的开关（S290–S291）

| 开关 | 默认 | 效果 | 代价 |
| --- | --- | --- | --- |
| `search.provenStop` | **on** | `off` 时零成本赢不再置 `provenOptimal`，搜索跑完预算 | 节点数大增 |
| `search.keyExtras` | **off** | `on` 时把药水槽、遗物计数、球 evoke/passive 并入键 | 合并减少、节点上升 |

S290（9/9）：默认臂三行与 S289 早停开逐项相同（10,023,597/14；10,023,038/5；10,023,277/21），
`off` 臂复现早停关行（10,035,593/30,000/7；10,035,032/30,000/8；10,035,271/26,409/9）且
`proven=false`。S291（6/6）：默认 off 时 S287 两类碰撞仍不可见；on 时可见；再关掉后重新相等。
Part D 用 S285 的 F2/V0/20k 做回归对照，score 与 bestAt 全部一致 ⇒ 默认 digest 无漂移。
Part E（仅记录）：F2 + Fire Potion，off→on 的 transpositions 254→248 / 625→613 / 978→978，
分数不变——键变细只改变合并，不改变最优线。

一个诚实的插曲：S291 首版门禁把 S285 表的 `bestAt` 列当成了节点总数去断言，20k cap 下
nodes 必为 20,000，于是误报 FAIL。逐列核对后确认是**门禁抄错列**，不是搜索回归；
修正为断言 `bestAt`、`nodes <= 20000` 后 15/15 通过。

## 9. 第 7 轮：造一个真正难的夹具（S292，F4–F7）

前六轮的夹具收敛太快（214–4,350 节点），任何「省节点」的差异都被压平。硬夹具的判定
（每夹具 ≥2/3 seed 同时满足）：

1. `bestAt > 8000`；
2. 8k 节点阈值时的最好分 < 最终分；
3. 同 seed 下 V4 或 V5 的 score 或 steps 与 V0 不同。

80,000 节点 / 240 s。四次尝试：

| 夹具 | 内容 | 实际 nodes / bestAt | hardSeeds |
| --- | --- | --- | --- |
| **F4** | Cultist + JawWorm + LouseNormal；5×Strike_R / 4×Defend_R / Bash / Shrug It Off / Pommel Strike | 12.7k–33.3k / 7.4k–12.8k | **2/3** |
| F5 | Looter + LouseNormal + Feed + Fire Potion | 1.3k–4.4k / 694–1,273（proven） | 0/3 |
| F6 | F4 三怪 + Feed + Fire Potion | 5.8k–13.7k / 2,674–12,964 | 1/3 |
| F7 | 单只 GremlinNob（85 HP）+ Feed + Fire Potion | 5.7k–12.4k / 4,124–11,325 | 0/3 |

F5 失败因为 **Looter 会逃跑**，战斗在 1,348–4,350 节点就结束；F6/F7 失败因为 **药水 + Feed
让战斗变短**。夹具一旦定义就不按 seed 调参，也没有为了过闸换怪；药水矩阵线就此终止。
F5/F6/F7 保留为对照组（S292 只记录不断言）。这一轮的直接收获是方法论的：**「难」不是
加怪、加卡就有的，它取决于状态空间的大小和分歧出现的时机**。

## 10. 第 8 轮：F4 硬夹具矩阵（S293）

80k cap，V0–V5，3 seed，**54/54**。V0 在 12.7k–33.3k 节点自然穷尽（`proven=false`，未打到
cap），bestAt 位于总节点的 22%–87%：

| seed | V0 score / nodes / bestAt | V1–V3 | V4（targetFocus off） | V5（diversity off） |
| --- | --- | --- | --- | --- |
| 9401 | 9,976,847 / 21,974 / 12,783 | 与 V0 逐位相同 | +2,002（bestAt 2,435） | +2,009（bestAt 1,861） |
| 9402 | 10,000,842 / 12,702 / 11,065 | 与 V0 逐位相同 | −5,995 | +3,996 |
| 9403 | 9,999,568 / 33,270 / 7,379 | 与 V0 逐位相同 | −10,000 | 0（但 46,591 vs 33,270 节点） |

结论：

1. V1–V3 在硬夹具上仍然是零影响，可以排除。
2. **V4/V5 首次出现真实、双向的差异**（同一夹具 +2k 与 −10k 并存），方向随 seed 变 ⇒
   更不能改默认，但这是「保留策略」值得做实验的第一个依据。
3. 9403 需要 33,270 节点，说明 20k 预算会截断这类盘。1.8 应优先重排**预算/保留策略**，
   而不是继续动键。

## 11. 第 9 轮：套件收尾（K）

S292 只对 F4 断言硬度，F5/F6/F7 只记录；删除未运行的 S294；S293 代码不动。复核
`-Gates "S292,S293"`：**91/91 PASS**，S293 的 18 行与 H 轮**逐行相同**。任务 H 正式关闭。

## 12. 这一版带走了什么

- 正式默认值：**零改动**。搜索默认行为与 1.6.10 相同，`search.provenStop` 默认为 on、
  `search.keyExtras` 默认为 off，与 master 逐字节一致（S290/S291 已验证）。
- 可 opt-in 的正确性修法：需要「不漏掉先掉血后回血的高分线」时关 `search.provenStop`；
  需要区分药水/遗物计数的薄碰撞时开 `search.keyExtras`。
- 测量仪器：`bestAt` / `bestUpd` / 分数-节点曲线 / 硬夹具 F4，以及 11 道门禁，供 1.8 复用。
- 被数据否掉、不要再翻出来的方向：RNG 入键、dominance、turnPlanOff、多样性关闭、
  targetFocus 关闭作为默认、「连续无改进就停」的通用早停、20k 就是最优的假设。

## 13. 复跑

在装有游戏与 mod 的机器上（门禁会换入被测 jar，跑完自动还原官方 jar）：

```powershell
powershell -NoProfile -File tools\build.ps1 -Jdk "<JDK 路径>"
powershell -NoProfile -File tools\run.ps1 -Gates "S290,S291"
powershell -NoProfile -File tools\run.ps1 -Gates "S292,S293"
```

每道门禁都会在控制台打印逐格数字与断言结果；断言失败时同时列出期望值与实测值。

## 14. 不可比项（读表前必看）

- `plan=` 哈希含每进程重建的卡牌 UUID：**只能在同一进程内比**。跨运行比 score / nodes /
  steps / bestAt / proven。
- 聚焦与全 mod 环境的 `ms` 不可比（mod statics 遍历量不同）；nodes 与 bestAt 可比
  （S283 两环境逐格相同）。
- 20k/30k 行的「最优」只在该预算内成立，见第 5 轮。
- 同分不代表同线；判线用步骤内容，不用分数。
