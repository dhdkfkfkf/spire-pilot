# 搜索架构选项：A 可做，B 永久否决（2026-10-30 决策记录）

这份文档回答三个问题，并把答案钉在仓库里，免得以后又从头讨论一遍：

1. 除了现在的做法，还能怎么提速（A / B / 多进程分别是什么）；
2. 哪些对 mod 有影响、哪些没有；
3. 为什么「数值代理」（B）在这个项目里永久不做，什么条件下才值得重开。

代码与门禁的现状：安装版 jar 套件 **420/0**（2026-10-30 12:04），成本口径见 `docs\PERF.md`。

## 2. 为什么 B 永久否决（四条理由 + 旧项目实证）

### 2.1 保真度的成本不在写规则，在证明规则和真引擎一致

原版支持面是 370 卡 / 43 药水 / 190 遗物 / 66 怪物。写 370 张卡的规则也许两周能糊出来，
但要达到 STS2 那种敢报最优的程度，必须逐卡/逐遗物/逐怪做**差分测试**：同一局面、同一动作序列，
代理与真引擎逐步比对 HP/格挡/能量/抽牌/状态层数。差一张卡的一个分支，就是一个静默错误。
工期上这跟每张卡写一遍等价，只是写的是测试而不是规则。

### 2.2 mod 内容在代理里不存在（结构性冲突，不是工作量问题）

代理要算一张牌，前提是有人把这张牌的效果写成规则。
mod 的卡是运行期才加载的类，**不可能**在代理里预先存在：

- 要么把它排除在代理外（那 mod 场景就退回真引擎，等于没加速）；
- 要么为每个 mod 卡手写规则（每个 mod 都要维护一套，永远追不上）。

而我们的项目定位恰恰是任意 mod 也能跑，只是默认未认证（见 `docs\MOD-CONTRACT.md`）。
现在装的 9 个未认证战斗钩子（ninjaMod 的 postDraw/postExhaust/onCardUse/postEnergyRecharge/postPowerApply/postBattle、
MintySpire、RelicStats）在真引擎路线下是结果打折，在代理路线下是根本不存在。

### 2.3 双份语义 = 两个 bug 面

代理与真引擎一旦不一致，就要判断是代理错了还是引擎行为没理解；
而这个判断本身又要靠真引擎对账，绕回原点，还多维护一套规则。
我们现在的每一行判定都只有一份实现：游戏自己。

### 2.4 旧项目就是实证：26075 个文件、1511 个 .cs、540 个 .java，仍然比 STS2 错得多

`C:\Users\YOKI\Documents\deepseek-harness\sts1-combat-solver`（旧项目）走的就是 B：

- `src\main\java\combatsolver\model\cards\` 只有 **29 个文件**（`CardEffectRegistry.java` + `VariantUpgradeRules.java` + 少量），
  即参数化规则 + 注册表覆盖 370 张卡；
- `src\referee\java\combatsolver\EngineCorpus.java:17` 的注释已经写明它需要真引擎当裁判：
  `In-game capture of engine-side corpus: the referee truth M2's differential needs`；
- 即便如此，它的 bug 类型是某张卡在某个组合下参数不对（X 费、多段攻击、弃牌触发顺序、升级差异），
  不是漏了一张卡——这正是参数化注册表的固有失效模式。

结论：把规则重写一遍不会变准，只会把一个已知正确的引擎换成一个需要被证明正确的引擎。

### 2.5 什么条件下才重开 B（写下来，免得以后凭感觉翻案）

三条同时成立才值得重新评估：

1. 有**自动生成的差分语料**（能让真引擎批量产出状态→动作→状态样本，代理按样本回归，而不是手写测试）；
2. 有**mod 内容的代理生成器**（从类字节码/反射元数据自动推导规则，而不是逐 mod 手写）；
3. 需求变成**跨战斗/整局规划**（那时真引擎逐节点跑的成本才真正不可接受——单场战斗我们已经够用）。

现在的三条都不成立，所以 B 标记为 **❌ 永久否决**，不是以后再说。

## 3. A1 怎么做（选择性加深：用短程 rollout 改善排序）

### 3.1 它解决的是哪个问题

现在的扩展是「每个候选 fork → 应用动作 → 用静态启发式 `Solver.score` 打分 → 排序 → 留 beam」。
静态分数看不到打完之后对面还手会怎样，所以 beam 里经常混进看起来赚、实际上要挨打的线。
A1 的改动只有一处：**把静态打分换成真引擎短程试算的打分**，其余（真引擎、判定、门禁）不变。

### 3.2 算法（落在 `Solver.expand` / `expandAndRecord` 的候选排序处）

```text
for each candidate a in legalActions(node):
    child = fork(node); apply(child, a)          // 现状已有：fork 194us + apply 0.86-2.6ms
    if child is terminal: score = engineScore(child)
    else if rolloutBudget > 0:
        probe = fork(child)                      // child 保留，用于真正展开
        rollout(probe, depth=2, policy=greedy)   // 每步：打最高价值可用牌，目标=最低 HP 怪
        score = blend(engineScore(probe), engineScore(child))   // 末态 0.7 + 当前 0.3
    else: score = staticScore(child)             // 预算用完 -> 自动降级为现状
rank by (won, deathSaves, deficit, score); keep top beam
```

- **rollout 预算独立**：一次 solve 只给总预算的 15%，用完静默降级；
- **只在候选数 > beam 时才试算**（候选本来就装得下，试算纯浪费）；
- **深度自适应**：距叶子 < 3 层时 depth=1；
- **可关闭**：`-Dsts1solver.search.rollout=0` 一键回到现状，门禁同时跑开/关两种。

### 3.3 成本数学（为什么只敢承诺 1.2–2×）

用 P1-2d-2 / P1-2f 的实测口径：**fork 约 194us，一次 apply 约 0.86–2.6ms**（apply 是 fork 的 5–13 倍）。

| 每层（beam=32） | 现状 | A1 |
|---|---|---|
| 32 个候选各一次 fork+apply | 48–90ms | 48–90ms |
| 前 2x beam 个候选再加 rollout（1 fork + 2 apply） | 0 | 约 35ms |
| 合计 | 48–90ms | 83–125ms |
| beam 收到 12 时 | — | 约 44–60ms |

也就是说：**A1 只有在收窄 beam 不丢质量被实验证实后才赚钱**，最乐观 2×，最坏 1×（白花 rollout 预算）。
这就是它必须先做对照实验、而不能直接上线的理由。

### 3.4 风险清单（症状 / 根因 / 缓解）

| # | 风险 | 症状 | 缓解 |
|---|---|---|---|
| R-A1 | **排序偏差**：试算深度不够，把真正的胜线排到 beam 外 | 同一局面 A 开比 A 关赢得更少 | 判定仍由真引擎；provenOptimal/win 语义不变；门禁场景集开/关对照，要求关能赢的开也必须赢 |
| R-A2 | **所有路线都会死失真** | A 剪掉了线，面板却说所有路线都会死 | frontierExhausted 在 A 下显示为 A 下前沿跑尽；措辞分级（S58）重校准；A 关闭时才允许说所有 |
| R-A3 | **预算被试算吃掉** | 总节点数反而下降、深度变浅 | 独立 15% 预算池 + 用完自动降级 + 日志 rollout=on/off/off(budget) |
| R-A4 | **rollout 策略自身有 bug** | 试算荒谬（明明能挡却不挡） | 策略复用 Legal.actions + Solver.score，不新写规则；门禁钉同一局面贪心 3 步内不产生非法动作 |
| R-A5 | **与 P2-2d 窄深 pass 冲突** | Boss 战反而变慢/变浅 | 实验矩阵含 Boss；窄深 pass 下默认关 rollout |
| R-A6 | **mod 影响** | 无 | rollout 仍走真引擎，与现状同一保真度 |

### 3.5 验收协议（先实验，后决定）

- 场景集：`-Mode cost-all` 的 5 场 + A20 四地精 / 史莱姆老大 / 觉醒者 各 3 个种子；
- 指标：win 数（不得下降）、平均 hpLoss（不得上升）、nodes、wall time；
- 通过线：**≥1.3× 且质量零回退**；1.1–1.3× 记为勉强；<1.1× 标记 ❌ 不落地并记录数据；
- 门禁：S59（零伤最优）、S58（措辞分级）、全量套件在 rollout=0 与 rollout=1 下各跑一遍。

### 3.6 实测结果（2026-10-30，❌ 否决）

按 §3.5 的协议做了开/关对照（`-Mode rollout`，REAL_DECK 30 张、seed=501、每场 off/on 同预算）：

| 场景 | rollout | 赢 | 掉血 | 节点 | 墙钟 | 试算耗时 |
|---|---|---|---:|---:|---:|---:|
| JawWorm（8s） | off / on | 是 / 是 | 0 / 0 | 1780 / 1918 | 2808 / 2809ms | 0 / 393ms |
| SlimeBoss（15s） | off / on | 是 / 是 | **32 / 65** | 3501 / 2825 | 15004 / 15049ms | 0 / 4094ms |
| TheCollector（20s） | off / on | 否 / 否 | – | 3976 / 2857 | 20022 / 20069ms | 0 / 4958ms |

结论：**加速为负、质量回退 → ❌ 不落地**。三条原因：
1. 每个候选的试算 ≈ 一次 fork+install+apply+readBack，等于把 expand 做两遍，吃掉 20–25% 墙钟；
2. 同一预算下节点反而少 19–28%——试算挤掉了本该展开的分支；
3. 1 步贪心分把「眼前伤害低、后续更糟」的状态排到前面（SlimeBoss 掉血 32→65）。

代码保留、**默认关闭**（`-Dsts1solver.search.rollout=true` 才开），只用于复现实验与门禁 S68；正式搜索路径不变。
登记与 P1-2e/P1-2f 同类（实测否决）。证据 `evidence\A1-ROLLOUT-20261030.txt`。

## 4. A2 是什么（2026-10-30 复核结论：①已存在，②决定不做）

`Solver` 已经有 `Digest`（状态摘要）与 S19 的跨层重复统计。原计划 A2 做两件事：

1. **同状态合并**：同一层里 digest 相同的节点只保留最好的一个；
2. **支配剪枝**：A 支配 B（HP、格挡、能量、回合都不差、怪物总血不更高、手牌多重集覆盖 B）就把 B 丢掉。

### 4.1 同状态合并：已经在代码里，没有收益可拿

复核 `src\main\java\sts1solver\search\Solver.java`：

- 层内合并在 `nextMap`（`:516`）已经做了：`if ((node3 = nextMap.get(choice2.digest)) != null && n22 <= node3.score) continue;`；
- 跨层去重在 `hashSet`（`:457`）：`if (!hashSet.add(object.digest)) continue;`。

而 digest 相同意味着**同一个状态**，`score` 里含掉血量、怪物总血、格挡、存活数这些状态量，所以同 digest 的节点分数必然相同——
先到先得和“保留更优者”是同一件事。**这一条不是没做，是做了以后没有可省的东西**（省下来的是 0 个节点）。

### 4.2 支配剪枝：决定不做（收益 1.1–1.3×，风险是不 sound 的剪枝）

要判断“A 支配 B”需要给每个节点额外存一份状态向量（HP / 格挡 / 能量 / 回合 / 怪物总血 / 存活数 / **手牌多重集**），
并且每层在 ≤128 个节点之间做 O(n²) 覆盖比较。两个具体问题：

1. **手牌多重集覆盖不是充分条件**：卡组里有 `Corruption`/`Barricade`/充能球这类改变资源语义的东西，
   “我多一张牌”不等于“我的未来是对方的超集”；要证明它 sound，得按牌逐张写规则——那正是 B 路线（数值代理）的老坑。
2. **不 sound 的剪枝违反 R10 推论 2**：近似必须可开关，且“关能赢的局面开也必须赢”。这条在真实牌组上无法靠少量门禁验证，
   只能靠差分测试矩阵——成本远超 1.1–1.3× 的收益。

结论：**A2 的支配剪枝登记为“分析后否决”**，不再排期。重开条件与 B 相同（见 §2.5 的精神）：
有人能给出可证明的支配关系（例如只对“完全相同的遗物+牌组+怪物”且手牌多重集相等的情况剪），并且有成规模的差分证据。

因此 A0/A3 之后真正剩下的只有 **A1（排序改进，可选）**——它已在 §3.6 被实测否决（更慢更差），排序这条路到此为止。

## 5. 算法来源（不需要新论文）

- **骨架**：beam search + 四档 portfolio，已有；宽度/份额对齐 STS2 `beam-width-portfolio.md`（R9）；
- **A1 的两块**：selective deepening（beam 的 lookahead）、greedy rollout policy，都是教科书组件，零新依赖；
- **STS2 里值得抄的已经抄了**：停止规则（R9）、边界原因、路线排序键序（R3/R4）；
- **不抄的**：BFWS 新颖性搜索、置换表、神经网络估值——与跑真引擎的成本结构不匹配，换过去等于重写搜索层。

## 7. 用户 2026-10-30 的方案：不排除 + 用满预算（A0 / A3，优先于 A1）

用户 m06700 三条要求：

1. **不要把可能最优的答案排除了**（浅层打分只代表"两步内更好"，全局最优的线可能被 beam 丢掉）；
2. **先算可能最好的路线，没拿到无伤就去算其他可能全局更好的路线**；
3. **算到上限之前不许停**（预算没用完就收工时，必须说清是"证明过了"还是"没算"）。

这个方向比 A1 更对，而且先做它更划算。原因：beam 截断本身就是"永久排除"——被挤出 beam 的节点直接 `continue` 丢弃（`Solver.java` 里 `nextMap` 只留 top-N），
A1 只是把排序算得更准，仍然在丢。

### 7.1 现在的代码确实会提前停（两处，已核实）

| 位置 | 行为 | 后果 |
|---|---|---|
| `Solver.java:502` 与 `:1178` | 首胜之后只再搜 `REFINE_LAYERS = 8` 层就 break，**不看 hpLoss** | 掉 16 血也算"找到了"，后面的线不再搜 |
| `Solver.java:91` 与 `:1387` | portfolio 固定 4 档、份额 35/25/25/15；某档提前结束，**没花完的份额不回收** | 四档都找到带伤胜线时，整套会在预算用尽前收工 |
| `Solver.java:112` | `win && hpLoss<=0 && 已过半` 时提前 break portfolio | 零伤但用过药（未证明最优）时提前停 |

实测：F8 在史莱姆那场预算 `5000ms`，`solve: win ... hpLoss=16 ... 908ms` —— **4.1 秒没花**，
而这 4.1 秒本来可以去试"别的路线"。用户看到的"预计战损 16"就是这 8 层内的产物。

### 7.2 三个改动（按性价比排序）

**A0 用满预算（约 1 天，零正确性风险）**

- 删掉"首胜后 8 层截断"：胜线不再触发停止，只有 `provenOptimal`（零伤 + 零药）才停；
- 份额回收：某档提前结束后，剩余时间传给后面的档；四档跑完仍未 `provenOptimal` 且预算有剩 → 继续更宽/换 tie-break 的追加档，直到预算或节点上限；
- 面板与日志显示"预算用了 x/y ms"与"还有 N 条候选没展开"；
- 代价：F8 从 "0.9 秒出答案" 变成 "用满 5 秒"。这正是用户要的（不能无伤就继续算），但需要接受计算变慢。

**A3 延后队列，不丢弃（约 2–3 天）**

- 把"挤出 beam 就 `continue`"改成"放进 deferred 列表（只存 path + score + digest，不存 World）"；
- 每轮从 deferred 里按估计分提升若干条（晋升时按 path 重放物化，成本 = 深度 × apply）；
- 只有两种情况允许真丢：①内存上限；②被支配（A2 的可证明更差）；
- 这样"两步内更好"只影响**先后**，不影响**有没有机会**——正是用户第 1、2 条。

**A2 支配剪枝（约 1–2 天，与 A3 配套）**

- 同状态合并 + 可证明支配（HP/格挡/能量/回合不差、怪物总血不更高、手牌多重集覆盖）→ 这是唯一"可以安全排除"的排除；
- 顺带把 deferred 列表压小，降低 A3 的内存压力。

### 7.3 诚实边界（必须写进面板）

- "不排除" ≠ "遍历所有世界线"：预算内仍然要决定先展开谁，A3 保证的是"不被浅层打分永久删除、按估计排队"，
  不是"已证明所有线"（穷尽指数级状态做不到，STS2 也做不到）；
- 唯一能说"证明最优"的停止条件是**零伤 + 零药**（R9，对齐 `IsProvenZeroDamageRoute`）；
- 其余情况一律说"预算内最好（未证明）"，并给出"还有 N 条候选未展开"。

### 7.4 验收

- 预算用满率 ≥ 95%（除 `provenOptimal` 与前沿跑尽两种合法提前停）；
- 同一局面：A0 的 hpLoss 不高于旧版（因为多搜的线只会更好）；
- 日志/面板新增 `budget used=x/y ms`、`deferred=N`、`unproven=true`；
- 全套门禁在 A0 下重跑（S59 的零伤最优必须仍然成立，S58 措辞分级按新语义校准）。

### 7.5 与前面几节的关系

- **A0 + A3 + A2 是"正确性对齐用户意图"的改造**（先做）；
- **A1 降级为排序质量改进**（后做、可选），它只让 deferred 队列的顺序更好，不能替代 A0/A3。

### 7.6 上限三档（P2-58，用户 m24721）

所有「截断分支」的上限都走 `settings.txt`，一个主档 + 每个键可单独覆盖（读一次缓存 1 秒，改完下一场生效）：

```
limits=high              # low | high | unlimited（同名中文「低 / 高 / 无限制」也可以）
limits.pile=unlimited    # 牌堆单选分支上限：low 12 / high 28 / 无限制
limits.hand=high         # 手牌单选分支上限：low 16 / high 36 / 无限制
limits.combos=low        # 多选组合数：low 8 / high 48 / 无限制 5000
limits.screens=high      # 一个动作最多应答几屏：low 2 / high 4 / 无限制 8
limits.deferred=low      # A3 停车场上限：low 500 / high 2000 / 无限制
limits.promotions=high   # A3 每次搜索的晋升数：low 4 / high 6；cap 20 / 60 / 200
limits.beam=low          # 束宽上限：low 45 / high 96 / 无限制 256
limits.layers=low        # 层数：low 200 / high 400 / 无限制 4000
```

- **单选（牌堆/手牌）不截断是默认行为**：一次选牌的全部候选都会成为搜索分支（对应 STS2 `CardChoiceSupport.BuildChoices` 的 `branchLimit = max(limit, Options.Count + skip)`）。`limits.pile/hand` 只在一次动作有多个屏、需要限制组合爆炸时起作用。
- **多选**：先枚举组合，按选项名次和的升序排，再按 `limits.combos` 截断；「什么都不弃」与「最差 1..k 张」的累积前缀始终保留。
- **多屏**：`limits.screens` 是屏数上限，组合总数由 `limits.combos` 再截一次（头追 5×7=35 默认全算）。
- **`unlimited` 不等于关掉物理**：堆守卫（`Solver.heapLimitMb`，默认 65% 堆）与秒/节点预算照旧生效，所以无限制不会把游戏卡死，只是不再静默砍分支。日志每次搜索打一行 `limits=… pile=… hand=… combos=… screens=…`（只在变化时打）。
