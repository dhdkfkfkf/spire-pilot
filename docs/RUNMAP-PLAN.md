## 1. 整局不做全局最优搜索，但选路本身要搜

整局不做「把后面每场战斗都排一遍」：那是 分支数 × 每场求解时间 的指数问题。
MVP 只在**每个决策点做一次有限深度的期望值搜索**，战斗交回真引擎：

1. 地图上选下一个节点：对本幕剩下的 15 层做 Beam Search（不是只看下一层），边权是**期望收益（单位 HP）**，见 §3；
2. 进房间后按屏处理（事件/营火/商店/宝箱/战后奖励，见 §4）；
3. 进战斗就把战斗交给 `Solver.solvePortfolio`（现有 F8 那条路径，含预算/分帧）；
4. 战斗结束继续走，直到 Boss 打完。

两件事要分开看：**路线怎么选**（本文件的重点，离线可算、便宜）与**战斗怎么打**（现成的搜索，贵但在真引擎上）。

## 2. 地图事实（已 javap 核实）

- `AbstractDungeon.map`：`ArrayList<ArrayList<MapRoomNode>>`，索引 = 层 y；每层 1–6 个节点。
- `MapRoomNode`：`public int x, y; public AbstractRoom room; boolean taken;`，连接用 `getEdges()` / `isConnectedTo(other)` / `getParents()`。
- `AbstractDungeon.currMapNode` 是当前节点，`AbstractDungeon.nextRoom` 是待进入节点；`setCurrMapNode(node)` 设当前。
- 节点类型：`MonsterRoom` / `MonsterRoomElite` / `EventRoom` / `RestRoom` / `ShopRoom` / `TreasureRoom` / `MonsterRoomBoss`；未点开的节点 `room` 可能为 null（地图上显示 ?）。
- 可走性：只走 `currMapNode.isConnectedTo(candidate)` 的节点；`leftRoomAvailable/centerRoomAvailable/rightRoomAvailable` 只是 UI 标记。
- **? 房间的类型是算得出来的**（不是隐藏信息）：游戏自己在进入那一刻用 `EventHelper.roll(new Random(Settings.seed, eventRng.counter))`
  决定它变成 事件/精英/普通怪/商店/宝箱（`dungeons/AbstractDungeon.java:1743-1759`）。同一份 seed + counter + 同一份概率，
  我们就能算出同一个答案，见 §3.4；地图上还能直接读到「哪个精英带绿钥匙」（`MapRoomNode.hasEmeraldKey`）。
- 不读「还没生成的东西」：不读 `AbstractDungeon.monsterList` 里未生成的真值、不预读牌堆顺序、不预读事件选项的结果
  （这些要么还没定，要么读了就是幽灵信息）。

## 3. 选路 v2：期望值搜索（EV + Beam Search + 硬安全），学习模型只做先验

### 3.1 为什么换掉第一版
第一版给每种节点一个固定分（宝箱 10、营火 6…）再加条件修正，问题有三个：
1. **单位不统一**：宝箱 10 分和营火 6 分谁更值钱完全靠拍；掉 30 HP 与拿 1 个遗物无法比较；
2. **只看一层**：看不到「这层打精英，后面 3 层没有火堆」，而这正是跑图最难的地方；
3. **不可评估**：没有「这条线期望掉多少血」这种可以对照真结果的数字。

新版三件事：①把一切折成 **HP**（唯一能跨节点比较的单位）；②对整幕做 Beam Search；③用真引擎测量「打这一场要掉多少血」。

### 3.2 目标函数
对一条候选路线 `r = (n1..nBoss)`，累计

```
score(r) = Σ_i  gamma^(i-1) * value(n_i)
value(节点) = E[拿到的东西折成 HP] - E[掉的血] - riskAversion * 该节点掉血的不确定性
```

- `gamma = 0.9`：越远越不确定，给折扣；
- `riskAversion`（默认 0.5）：面板给「更稳 / 更均衡 / 更贪」三档，只改这一个系数；
- 同一局面同一 seed 结果确定（浮点比较用 1e-6 容差 + 固定平局键）。

### 3.3 折成 HP 的换算表（可调，写进 settings.txt 备份）

| 收益 | 折算 | 依据 |
|---|---:|---|
| 1 点 HP | 1.0 | 基准 |
| 1 次营火（休息） | `min(0.3*maxHP + (Regal Pillow ? 15 : 0), maxHP-HP)` | `ui/campfire/RestOption.java:25`：0.3×maxHealth，Regal Pillow +15 |
| 1 次营火（升级） | 2.5 + 0.5×该牌 `cardValue` 档位 | 升级≈一张牌强度上调，MVP 粗估 |
| 1 张普通/罕见/稀有卡 | 0.8 / 1.5 / 3.0 | 与现有 `cardValue` 同量纲的粗估 |
| 1 个遗物 | 4.0（平均） | 路线对比表里遗物≈1.3–5 个/幕，按平均收益摊 |
| 1 瓶药水 | 3.0（有药水遗物 ×1.5） | 药水在 Boss 战≈10–20 HP，摊薄 |
| 1 金币 | 0.06 | 牌价 `AbstractCard.getPrice`：普通 50 / 罕见 75 / 稀有 150（`AbstractCard.java:1900-1918`），再 ×`merchantRng(0.9,1.1)`（无色牌 ×1.2）；删牌 75 起每次 +25（`ShopScreen.java:85,266`）；金币收入：普通战 10–20、精英 25–35、Boss 100±5（进阶 13+ ×0.75，`AbstractRoom.java:279-315`） |
| 1 次精英 | 遗物 4.0 + 金币 25×0.06 + 卡 1.0 − E[掉血] | 见 §3.5 |

### 3.4 未知房间（?）：用游戏自己的 roll 精算，不猜分布
`slayspiredb` 的分布表是「所有人平均」，而我们手里有 seed —— **这一个** ? 会变成什么可以直接算：

```java
Random dup = new Random(Settings.seed, AbstractDungeon.eventRng.counter); // 与游戏同一口径
EventHelper.RoomResult type = EventHelper.roll(dup);                     // 同一个函数，同一份概率
```

事实（`dungeons/AbstractDungeon.java:1743-1759`、`helpers/EventHelper.java`）：
- 地图上的 ? 只是 `EventRoom`；真正类型在**进入瞬间**由上面那行 roll 决定，然后 `generateRoom` 换成
  `MonsterRoomElite / MonsterRoom / ShopRoom / TreasureRoom / EventRoom`；
- `eventRng` 只在这次 roll 消耗一次，滚完 `eventRng = duplicate`（counter 前进 1）→ **整幕的 ? 序列可以连锁推演**：
  第 k 个 ? 用当时的 counter 再滚一次即可；
- 概率表是静态量且会**累积**：滚到精英清零、没滚到精英 +0.1；怪总是重置 0.1；商店没滚到 +0.03；财宝没滚到 +0.02；
  `floorNum < 6` 时精英格为 0；当前房间是商店时商店格为 0；`Juzu Bracelet` 把怪改事件；`Tiny Chest` 第 4 次强制宝箱；
  `DeadlyEvents` mod 精英格翻倍。这些都写在 roll 里，所以**装 mod 也自动算对**；
- 副作用必须快照/还原，否则等于替玩家改了概率：`ELITE_CHANCE/MONSTER_CHANCE/SHOP_CHANCE/TREASURE_CHANCE`、
  `saveFilePreviousChances`、`Tiny Chest` 的 counter —— 又一例 `docs/JUDGMENT.md` R13 的镜像不变式；
- 推演时需要 roll 那一瞬间的 `floorNum`（进房前已 +1）与「上一个房间是不是商店」，这两个量在推演路线时都是已知的。

因此 §3.3 的 `value(?)` 不用加权平均，直接取推演出来的那一种的值。只有推演不可用时（读不到静态量 / mod 改了 roll 之外的逻辑）
才退回分布表（下表，来自 `slayspiredb.com/工具/路线对比表`）：

| 第 N 个 ? | 事件 | 敌人 | 商人 | 财宝 |
|---|---:|---:|---:|---:|
| 1 | 85% | 10% | 3% | 2% |
| 2 | 71.1% | 19% | 5.9% | 4% |
| 3 | 60.3% | 25.3% | 8.6% | 5.8% |
| 4 | 53.5% | 28.3% | 10.8% | 7.5% |
| 5 | 51.5% | 28.6% | 11.8% | 8.1% |

### 3.5 战斗掉血：用真引擎测，不查表
这是本方案与两个外部工具最大的差别：

- 普通战 / 精英：在沙盒副本上把「当前牌组 + 当前 HP/遗物/药水 + 进阶」对**本层可能出现的遭遇**跑一次快速求解
  （`Solver.solvePortfolio`，预算小：普通战 800ms、精英 2000ms，宽度按 §3.9 收紧），取 `hpLoss`；
- 遭遇集：从游戏自己的遭遇池按层/进阶取（`MonsterHelper` / `AbstractDungeon` 的遭遇列表），不是手写表；
- 缓存：`key = hash(牌组) + HP档 + 遗物集合 + 进阶 + 遭遇id`，命中直接返回；
  HP 只按 10% 档位分桶（避免每步都重算），档内线性插值；
- 拿不到胜线（`no-live-branches`）时按「最坏」处理：`E[掉血] = 0.6*maxHP`、并给该边一个 `danger` 标记（面板显示红色）。

### 3.6 搜索（Beam Search，不是贪心）

```
beam = [当前节点路径(score=0)]
for y in 当前层 .. Boss 前一层:
    for path in beam:
        for next in 该路径末端节点的可走边:
            v = value(next, state_after(path))   # 见 3.3–3.5
            push(path + next, score + gamma^(y-1) * v)
    按 score 降序保留前 BEAM_W 条（默认 8，可在面板调 4/8/16）
    硬安全过滤（见下）
  返回 top-3 条完整路线 + 每步的分项（掉血/金币/卡/遗物/火堆）
```

**硬安全不是加分，是过滤**（参考 route-plan 的 `RuleSafety`：安全约束不能靠权重抵消）：

| 条件 | 过滤 |
|---|---|
| HP < 50% 且该边是精英 | 丢弃（除非该层唯一出路） |
| 已连续 3 场战斗且下一步不是营火/商店 | 降级为最后候选 |
| 牌组 `attackRatio < 0.35` 且 HP < 60% 且下一步精英 | 丢弃 |

### 3.7 学习先验（route-plan 的 LightGBM，只做先验/平局/解释）
`Slay-the-Spire-route-plan-main` 的做法（已读完源码，见 §9）是：
48 个特征 → LightGBM 7 类（下一节点类型：M/E/R/$/?/B/T）→ 取 `log p(专家会走的类型)` 累加 → 层末截 beam。
**它的 label 是「专家下一步选了什么」**，学的是「像高手」而不是「更可能赢」；作者自己的 `final_config` 也写
`rule_weight = 0.0`（规则只做安全与解释）。我们用它的方式因此限定为：

1. **候选排序先验**：在 beam 里给 `w * log p`（默认 `w = 0.15`，可 0）作为 tie-break 与探索引导；
2. **解释**：面板写「模型认为这类选择与高手一致度 x%」，给人看；
3. **不参与**胜负判定，不影响 `Solver`；A/B 对照（0.15 vs 0）没提升就永久关掉。

接入前提（P4-1d）：

### 3.9 成本与预算
| 部分 | 单次成本 | 说明 |
|---|---:|---|
| 非战斗节点 EV | <1 ms | 纯算术 + 查表 |

### 3.11 三把钥匙与 Act 4（心脏）
要「一路打到心脏」，选路就得把钥匙算进价值。门槛与来源（均已核对代码）：

| 钥匙 | 来源 | 代价 | 我们能读到的 |
|---|---|---|---|
| 红（Ruby） | 任意营火选「Recall」（`ui/campfire/CampfireUI.java:91`，需 `Settings.isFinalActAvailable` 且还没有红钥匙） | 这一层不能休息/升级 | `Settings.hasRubyKey` |
| 绿（Emerald） | 本幕某个精英节点带钥匙（`AbstractDungeon.setEmeraldElite()` 随机挑一个 `MonsterRoomElite`），该精英被强化（力量 / 25% 最大生命 / 金属化 / 再生，数值随幕数涨），打赢掉 `EMERALD_KEY` | 打一个更强的精英 | `MapRoomNode.hasEmeraldKey`（`MapRoomNode.java:57`，地图上本来就会画钥匙图标） |
| 蓝（Sapphire） | 任意宝箱（`rewards/chests/AbstractChest.java:87`） | 拿钥匙就放弃同箱遗物（`RewardItem.java:307-316`） | 节点是宝箱 |

- 能不能开 Act 4：`Settings.isFinalActAvailable`（`core/Settings.java:631`）= 铁甲/静默/故障三个职业都赢过，且不是每日挑战/自定义挑战。
  本机 `preferences/STSPlayer` 里 `IRONCLAD_WIN/THE_SILENT_WIN/DEFECT_WIN` 都是 `true`，所以**能开**；
- 三把钥匙齐了才在 Act 3 Boss 后的门进 Act 4（`events/beyond/SpireHeart.java:140`）；
- Act 4 很短：休息 →「盾与矛」（Shield and Spear）→ 营火 → 心脏（750 HP 多阶段）；
- 选路影响（只往 §3.3 表里加三行，搜索与安全过滤不变）：
  ① 红钥匙 = 把一个火堆从「回血/升级」改成「拿钥匙」，血够时才做；
  ② 绿钥匙 = 这个精英的价值要加钥匙价值，但战斗难度也更高（若本幕只有这一个精英，绕不掉就认了）；
  ③ 蓝钥匙 = 宝箱价值减一个遗物（按遗物价值表算是否划算）。
- 缺钥匙时不要假装能打心脏：面板与日志明确写「本局缺 X 钥匙，只能到 Act 3」。

## 4. 房间与界面的处理（按玩家点击顺序）

| 场景 | MVP 行为 |
|---|---|
| 地图 | `setCurrMapNode(选中的节点)` + `DungeonMapScreen.close()` 走 `nextRoomTransition` |
| 战斗 | 交给 `Solver`（F8 同路径），赢后继续 |
| 战后奖励 | 拿卡：见 §4b（真引擎 A/B 对比 + 牌组缺口规则 + 允许跳过）；药水按 §3.3 折算是否值得满栏 |
| 事件 | 见 §4c：读选项合法性 → 真引擎试跑出「账单」→ 没有表时用硬规则兜底 |
| 营火 | HP < 60% 休息（`0.3*maxHP`）；需要红钥匙且 HP ≥ 70% 时选 Recall；否则升级 `cardValue` 最高的可升级牌 |
| 商店 | 只买得起且 `cardValue` 高于现有同费牌才买；删牌优先于买牌 |
| 宝箱 | 直接开；`isFinalActAvailable && !hasSapphireKey` 时拿蓝钥匙（放弃同箱遗物，按遗物价值判断） |
| Boss 遗物 | 三选一按遗物价值表（MVP 用固定顺序 + 日志记录） |
| 幕间（Act 过渡） | Act 1→2→3 都走；三钥匙齐了在 Act 3 Boss 后进门到 Act 4（盾与矛 → 营火 → 心脏） |

### 4b. 选牌 / 升级 / 买牌：分三层，先便宜后贵

> 术语：本节的「A/B」指**成对试打**——同一场遭遇，分别带候选牌 1 和候选牌 2 各打一遍比较掉血；
> 它不是 `docs/SEARCH-OPTIONS.md` 里的「方案 A / 方案 B」（那个是搜索架构二选一，已定选 A、B 永久否决）。

「哪张牌好」没有攻略表可查（mod 卡更没有），但**我们能让游戏自己回答**：把候选分别放进牌组，各打一遍接下来的真实遭遇，比掉血。
这是本方案相对其它跑图工具的第二个独有输入（第一个是 §3.5 的战斗掉血）。
**最终拍板的是 §4e 的 LLM 决策层**，这里的数字是它手里的证据，不是它必须服从的规则。

1. **硬规则先筛（<1ms）**：从 `AbstractDungeon.player.masterDeck` 统计牌组缺口（攻击/防御/能量曲线/群伤/成长/虚弱易伤），
   淘汰明显重复或绝对用不上的候选（同名已有 3 张、没有力量源时的 Heavy Blade、没有毒源时的 Catalyst 类）。
2. **真引擎 A/B（核心，≈0.3–0.5s/场）**：对每个候选建一个沙盒副本（当前牌组 + 这张牌），
   对**本幕代表性遭遇**（`EncounterPool` 取：单怪 / 多怪 / 精英 各 1 场）跑快速求解，比 `hpLoss`，平手再比回合数；
   选最优者。缓存 key = 牌组指纹 + 候选 id + 遭遇 + 进阶 + HP 档；平局容差 1 HP（避免噪声决定选择）。
   mod 卡走同一条路，自动算对（与 P3-2 同一个道理，不写第二份规则）。
3. **跳过也是选项**：三个候选都没比现有牌更好、或牌组已 > 25 张且没补到缺口 → 跳过；
   跳过的价值按「省下一次删牌 75 金 ≈ 4.5 HP」记账（§3.3 金币折算），而不是 0。
4. **升级**：调游戏自己的 `card.makeCopy()` + `copy.upgrade()` 取真实数值差（伤害/格挡/魔法数/费用），
   再按 §3.3 折成 HP；营火选「差值最大且这张牌确实会被用到」的那张，而不是按稀有度。
5. **商店买牌**：同一套 A/B，价格折 HP（0.06 HP/金）；前提是比「删一张弱牌」更值 —— 删牌仍优先（§4）。
6. **不做**：不做 ML 卡牌评分；`Driver.cardValue`（`drive/Driver.java:975`，伤害×2 + 格挡×2 + 魔法数×2 + 费用 + 稀有度）
   只是排序用的粗值，**不足以决定选牌**；不维护攻略表（mod 卡没有攻略）；不为了选牌改战斗判定。

成本：一次战后三选一 ≈ 3 候选 × 3 场 × 0.4s ≈ 3.6s；开启 §4d 的跨幕评估后是 3 候选 × 6 场 ≈ 7s（分帧，面板显示「选牌评估中」）；缓存命中 < 50ms。
预算不足或引擎出错时退回「硬规则 + `cardValue`」，并在日志写明是粗选。

### 4c. 事件怎么选（用户 m10590 第 2 问）

事件选项是命令式代码（`AbstractEvent` 里的 `buttonEffect` 闭包），**读不出「它做了什么」的声明**，所以先拿证据，再由 §4e 的 LLM 选择：

1. **能读的先读**：`EventOption` 的 label / `disabled` / `relic` 字段直接判合法性，非法选项剔除；
   要求特定遗物/牌/血量的选项按有无判断。
2. **真引擎试跑（我们独有的做法）**：试跑一份 run 状态，执行这个选项并推进到稳定，
   diff 出：HP / 最大生命 / 金币 / 牌组增删 / 遗物增删 / 诅咒 / 钥匙 —— 得到一张「账单」，再按 §3.3 折成 HP 比大小。
   - **沙箱只装状态，不装表现**（用户 m10602 第 2 条）：只复制 HP/金币/牌组/遗物/药水/诅咒/钥匙这些数值与牌，
     **不复制动画、音效、特效、UI 屏**——VFX 直接丢弃、`SOUND_VOLUME=0`、不渲染；试跑期间不 pump 任何表现层；
   - **函数引用要重造，不要克隆**：事件选项是捕获了事件实例的闭包（`buttonEffect`），直接克隆对象再调闭包仍会打到原件。
     正确做法是按事件 id 用游戏自己的注册表**重新实例化**一个事件（`EventHelper.getEvent(key)`），在那个新实例上执行选项，
     闭包捕获的就是副本；试跑结束后断开引用，不留在任何静态字段里（与 R13 同一条纪律）；
   - 已知限制：会自己打开选择屏的事件（删牌/升级/变牌）在副本里可能停住 → 记为 `needs-screen`，交给第 3 层；
   - 副作用必须完全丢弃（复用 B25/B26 的镜像与 `discardOnReadBack` 思路），事件试跑不许写存档；
   - 概率型结果（如「20% 拿到稀有遗物」）按期望算，用 3 次同 seed 试跑取平均，并在面板标「期望值」。
3. **表 + 硬兜底**：原版约 50 个事件可以做一张 50 行的结果表（一次性数据，不是第二套规则引擎）；
   没有表时用规则：无代价优先、HP 低不选掉血、牌组已厚不选加诅咒、缺钥匙时优先钥匙、能让牌组变薄的选项优先。
   mod 事件没有表 → 退回 1 + 3。

### 4d. 「战未来」的牌怎么权衡（用户 m10590 第 3 问）

本质是「现在没用、以后有用」的牌要跨时间比较。做法：

1. **评估集跨幕**：§4b 的 A/B 不只看本幕 3 场，再加「下一幕代表遭遇 2 场 + Boss 1 场」（遭遇池按幕取），
   跨幕权重 `gamma^幕数`（默认 0.9、0.55、0.33）；
2. **长战曝光**：成长牌（力量/敏捷/毒/充能球/每次打出加数值）只有在打得久的战斗里才显现，
   用 Boss 或高血量精英（≥150 HP）做那一场 —— 它们自然跑到 5–8 回合；
3. **稀释成本**：牌组每加一张记 **0.5 HP** 的「抽牌稀释成本」，所以只在 Act 3 才回本的牌，
   跨幕加权后仍为正才拿；这就是「薄牌组」的定量版本；
4. **生存优先的硬约束**：本幕 HP < 50% 时本幕权重 ×1.5，即「先撑过这一场再谈未来」；
5. **标签只作提示不作判据**：原版成长牌可列一张标签表（Demon Form / Inflame / Footwork / Corruption / Barricade…）
   用于面板解释「为什么拿它」；mod 卡没有标签，完全靠 1–4 的数字说话。

### 4e. 决策层：LLM 选，引擎给证据（用户 m10602 第 1/3 条）

**选择权在 LLM**，不用僵硬的加减分规则拍板。LLM 拿到的是「结构化证据」，不是规则表。

**输入**：幕/层、HP/最大生命、金币、进阶、牌组（每张：id/名称/类型/费用/是否升级/实际数值）、遗物、药水、
候选（三张卡或 N 个事件选项，含原文与数值）、本幕与下一幕的遭遇清单、**这块区域确实可能拿到的牌池**（本幕奖励池 + 商店 + 事件，含 mod 卡）。

**证据（引擎侧，优先给但可被质疑）**：§4b 的掉血 A/B、§4c 的事件账单、§4d 的跨幕加权；每项都带「怎么测的」，
LLM 可以采信也可以不采信，但必须写理由。

**联动（用户第 1 条：战未来 = 未来可能出现的牌）**：LLM 读卡池（原版 370 + mod 171）自己提出「这张牌和哪 2–3 张牌/遗物能配合」，
我们只验证它提的那几组（不做全卡库 O(n^2) 穷举）：`牌组 + 候选 + 配合牌` 各建副本跑同一组遭遇，看配合后是否显著优于单张。
- 只有 LLM 提出、且引擎验证通过的联动，才计入「未来联动价值」；
- 它提的配合牌必须来自**本局确实可能拿到**的池子（本幕奖励池/商店/事件），不是全卡库幻想；
- 面板与日志写清：`拿 A，因为和 B 配合（引擎验证：省 6 HP）` 或 `联动未验证，按单张算`。

**降级与可复现**：
- 没网络 / 没 key / 超时（> 8s）→ 退回 §4b 的数值路径，面板写「LLM 不可用，按数值选」；
- 每次决策写日志：状态指纹、prompt 摘要、模型回答、最终选择、理由；同指纹命中缓存 →
  「同 seed 两跑一致」这条验收改成**「决策可重放」**（重放命中的是缓存里的原决定）；
- 决策层不碰战斗判定：`docs/JUDGMENT.md` R10 仍然只有一份判定实现（真引擎）。

**接口**：mod 不内嵌 api key；`%USERPROFILE%\spire-pilot\llm.json` 放 endpoint/model/key（或读环境变量），
请求走 HTTP；一次决策 1–5s，面板显示「正在权衡（LLM）」。

**免费方案（用户 m10623 第 1 条）**：三条路，按「零成本 + 离线」优先；实现上都是一个 `LlmClient` 接口，`provider` 不同而已。

| 方案 | 成本 | 速度 | 质量 | 前提 | 结论 |
|---|---|---|---|---|---|
| 本机 Ollama（llama.cpp/GGUF） | 0（电费） | 7B Q4 全在显存约 30–50 tok/s，一次决策 2–5s；14B Q4 溢出到内存约 8–15 tok/s | 中（中文可用，复杂联动推理偏弱） | 装 Ollama（一次性）+ 下模型约 5GB | **默认**：断网也能用，隐私最好 |
| 免费额度云 API（Gemini Flash free / Groq / Cerebras / Mistral free / OpenRouter :free） | 0（有速率/日额度） | 1–3s | 高（70B 级） | 注册一次 key，免费政策可能变 | **优先**：质量最好，额度够跑图（一局约 30–60 次决策） |
| 付费 API（DeepSeek 等） | 一局约 ¥0.2（2000 in + 200 out × 50 次 ≈ ¥0.004/次） | 1–3s | 高 | 充值 | 兜底即可，确实很便宜 |
| 不用 LLM | 0 | 0 | 低（只按数值规则） | 无 | 最终降级路径 |

**推荐：三级链** 免费云 → 本机 Ollama → 数值兜底；任一级超时 8s 就下沉一级，面板明示当前用哪一级。
本机实测硬件：RTX 5070 Laptop（8GB 显存，WMI 的 AdapterRAM 常误报 4GB）、Ryzen 9 7845HX、31.2GB 内存（空闲 16GB）
⇒ 7B 量化模型可整块进显存；14B 量化需 9–10GB，会溢出到内存但仍可用（一次决策 5–10s，只在营火/商店这种低频决策可接受）。

**对 STS1 与 mod 的适配（用户 m10623 第 2 条）**：不训练模型「懂尖塔」，而是把它需要的那一小块真实数据喂进去。分四层，前三层现在就能做，第四层可选。

1. **上下文适配（首选，零训练）**：每次决策只喂该局面需要的东西——候选 3 张/几个选项的 `id + 中文名 + 类型 + 费用 + 原文(rawDescription) + 实际数值`、牌组摘要（按类型/费用分组，不逐张罗列）、可拿牌池摘要（本幕奖励池 + 商店 + 事件，**不是全库 541 张**）、当前 HP/金币/进阶/遗物。总预算 ≤ 4k token。
   - 为什么够：模型不需要「记得」某张卡，它需要「读懂这段文字并比较」。文字是游戏自己给的，所以**原版 370 张和 mod 171 张一视同仁**——mod 卡天然支持，不用为每个 mod 写适配。
2. **术语对齐**：中文客户端名 + 英文 id 双写（`Demon Form / 恶魔形态`）；附一张关键词小字典（力量/敏捷/易伤/虚弱/中毒/燃烧/格挡/能量/费用），避免模型把「中毒」理解成别的游戏的中毒。数值一律由引擎给（**不让模型算数**，它会算错）。
3. **自举知识库（RAG，比微调便宜）**：把「引擎验证过的决策 + 理由 + 结果」存成几百条小卡片（例：`A20 铁甲 60HP 第 8 层，候选 X/Y/Z → 拿 Y，因为与燃烧之血+重击配合，引擎测 3 场掉血 -6`）；按当前状态相似度注入 top-3。模型于是能看到「上次类似局面这么选、测下来更好」。
   - 数据来源全是我们自己的：solver 每步合法动作 + 结果 + 本轮 LLM 的理由。跑几局就有几百条。
4. **LoRA 微调（可选，暂不做）**：只有当 1+3 还不够时再做。数据用上一条的自举日志；本机 8GB 可 QLoRA 训 7B（几小时）。先做前两层，用「选牌与事件的人工抽检通过率」当尺子，不达标再上。

**mod 适配的真正难点不在模型，在引擎**：模型侧只要给原文就行；但要模拟一张 mod 卡，它得能被沙盒真实执行——这已由 P3-2 实测（171 张 mod 卡可构建、可搜、可重放；`-Mode coverage -AllMods` 501/541 可玩）。
余下的是 `docs/MOD-CONTRACT.md` 的三道门槛（mod 战斗钩子未认证、克隆/静态镜像未登记、自绘选择屏），与 LLM 无关。

## 4f. 分发形态（创意工坊「订阅即用」）与 mod 机制自举

### 4f.1 哪种组合能真正做到订阅即用

| 形态 | 订阅即用 | 额外成本 | 技术风险 | 结论 |
|---|---|---|---|---|
| **A. 纯引擎（不含 LLM）** | ✅ 是 | 0 | 低；jar 现在只有 543 KB | **今天就能上工坊**：上传走 ModTheSpire 上传器，依赖 BaseMod |
| B. 引擎 + 本机 Ollama | ❌ 需装 Ollama + 下一个 5 GB 模型 | 0 | 中（用户机器差异） | 作为**可选增强**：检测到 Ollama 就自动升级，否则走数值 |
| C. 引擎 + 免费云 API key | ❌ 需注册一次 key | 0 | 中（政策/限流会变） | 作为**可选增强**：填 llm.json 即生效 |
| D. 引擎 + 我们托管的代理服务 | ✅ 是（装好即用） | 服务器 + 额度（真实花钱） | 中高（滥用、隐私、可用性） | 想让 LLM 也「订阅即用」只有这条路 |
| E. 把模型打进 mod 包 | ⚠️ 理论可行 | 0 | 高（JVM 内推理、分发包几 GB、速度慢） | 不推荐 |

**结论（用户 m10641 第 1 条）**：能做到「订阅即用」的是 **A**；LLM 要么当可选增强（B/C，一次配置），
要么走 **D**（我们托管，才有真正的零配置，但要持续付费用并接受滥用/隐私问题）。
建议分发策略：**工坊先发 A**（默认就是完整可用的求解器），同一 jar 内建 B/C 的自动探测（检测到 Ollama 或配置了 key 就升级），
D 作为后续可选（先看有多少人真的用）。这样「订阅就能用」成立，且不为 LLM 阻塞发布。

### 4f.2 mod 机制自举（用户 m10641 第 2 条：先跑几局模拟对局，把机制给 LLM）

这是比「按 mod 源码写适配」好得多的路子：**让引擎自己观察 mod 的内容，再把观察写成模型看得懂的说明**。两个产物：

1. **机制卡 mechsheet（一次性、可缓存）**：对卡库里每张卡（先只做非原版卡）建一个干净战斗（99 能量、手牌只有这一张、场上一个高血量假怪），
   真打出去，前后 diff 状态 → 记录 id/中文名/类型/费用/目标/观测效果（伤害/格挡/抽牌/能量/增益层数）/触发时机/原文。
   - 成本：171 张 mod 卡 × 约 0.2 s ≈ **35 秒**，一次生成，存 %USERPROFILE%\spire-pilot\mechsheet\<mod指纹>.json；
   - 缓存键 = mod 文件指纹（版本变了才重算）；
   - 不确定性处理：一次试跑只能看到「无条件效果」；条件效果（若…则…）靠 rawDescription 关键词解析给出提示，再抽 5% 复跑核验；
   - 副产物：**这套试跑同时就是 mod 钩子的观测器**——哪个 BaseMod 订阅在何时被调，就是 MOD-CONTRACT.md 三道门槛里第一条的认证证据。

2. **自对局观察（每局/每 mod 一次，跑几分钟）**：用 mod 的牌组跑 N 场（N=20–50）模拟战斗（随机或 beam 出牌），记录
   「哪些卡一起出现时胜率/掉血明显更好」→ 协同候选表。这张表**不给 LLM 当判据**，只当「值得试的组合」提示（和 §4e 的联动提案同一条纪律：引擎验证才算数）。

**注入方式**：LLM 上下文里，牌和候选只带各自那一行机制卡（不塞整个 mechsheet），可拿牌池带摘要；
于是「模型没见过蕾忍/菜农的卡」这件事被消除了——它看到的是引擎刚测出来的行为，而不是猜的。

**为什么比写适配好**：mod 卡没有统一 schema（原文措辞、自定义机制各不相同），人工写适配要为每个 mod 维护一份；
自举是**对任何 mod 都一套流程**，且永远和当前版本一致。上限：引擎跑不动的机制（自定义 UI、跨战斗状态、事件屏）观测不到，
仍走 MOD-CONTRACT.md 的认证流程。

### 4g.1 三件事各自可选的方案（按成本/质量）

| 决策 | 方案 | 成本 | 质量上限 | 备注 |

### 4g.2 route-plan-main 到底怎么做的、弱点在哪

（`C:\Users\YOKI\Desktop\Slay-the-Spire-route-plan-main`，v1.0.0）

- 流程：读真实地图与状态 → 48 个特征 → LightGBM 输出 7 类下一节点类型的概率 → 逐层累加 `log(p) + 规则惩罚` → Beam Search → Top-3 路线，地图上高亮 Top-1。
- 监督信号：**人类高手的下一步选择**（`scripts/preprocess.py` 的公开 run 数据），所以它在学「像高手」而不是「更容易赢」。
- 规则库 v2：硬安全（低 HP 不推荐精英）+ 软规则（火堆/精英权重、精英后无火堆惩罚、后半段商店奖励、前置商店接精英、连续问号风险、强弱牌组倾向）。
- 已知短板（README/RELEASE_NOTES 自己承认或可推断）：①只有 A20 数据；②规则与模型口径不一致（训练配置 `rule_weight=0.0`，但 Java 端 edgePenalty 仍参与排序）；③不做选牌/事件；④无文字解释（release notes 的 Not included 第一条）；⑤仓库无 LICENSE，直接打包要作者许可。

### 4g.3 我们要怎么比它好（不靠更大模型，靠两件它没有的东西）

1. **目标函数换成「赢」而不是「像专家」**：它最大化专家动作似然；我们最大化 `E[通关]`，代理指标是折算成 HP 的期望掉血（§3.2/3.3）。同样的地图，我们的分数能回答「这条线大概掉几滴血」，它只能回答「专家更可能这么走」。
2. **用真引擎把 E[掉血] 测出来**：它没有模拟器，只能用特征猜；我们能把候选路线上的几场关键战斗（精英/Boss/第 3 场普通怪）真跑一遍拿数字。这是唯一能反驳「专家也会走这条路」的能力。
3. **状态更全**：逐张牌组、遗物、药水、HP、金币、进阶全进决策；它的特征只有路线层面的可达性计数与少量状态。
4. **覆盖三种决策、一套价值单位**：路线/选牌/事件都折算成 HP，互相可比；它只管路线。
5. **可解释、可验证**：每步给「预计掉 X HP / 营火回 Y / 精英给遗物 Z」，而且决策能 replay 复现（我们已有 digest 校验）；它的推荐无法验证是否真的更优。
6. **对 mod 天然成立**：我们的 E[掉血] 跑的是真游戏代码，mod 卡/怪自动算对（§4f.2）；它的模型只认原版符号，mod 内容一律失明。

**不是全盘否定它**：它的强项是有海量人类对局先验（我们短期没有）。所以定位是「**我们的搜索为主，它的先验只做 tie-break**」
（§3.7 已定：默认权重 0，A/B 有提升才开）。想要那份先验可以自己用公开 run 数据重训（不引入它的模型文件，避开许可证），或直接做成可插拔的 `Prior` 接口。

## 9. 参考：route-plan mod 的实现事实（已读源码，2026-10-30）

- 入口 `RouteRecommender.recommend(map,startX,startY,state,model,topN,beamWidth)`；逐层对 beam 每条路径算 48 特征 → 模型 7 类概率 →
  `score += log(p[type]) + RouteRuleLibrary.edgePenalty(...)`；层末截到 beamWidth；返回 top-N。
- `RouteRuleLibrary.edgePenalty` 是一个手写加罚分（火堆 +1.5、精英 +1.0、精英且下 3 层有火堆 -0.5、后半幕商店 +0.5、
  连续 ? -0.3×(streak-1)、连续战斗 -(streak-2)×0.8、低 HP 精英 -1.0 等）——它确实参与排序，和 `final_config.rule_weight=0` 口径不一致，
  属于我们对它的注意点（我们把安全做成过滤而不是分数）。
- 特征里最有信息量的一类是**可达计数**：BFS 1/3/5 步内能到几个精英/火堆/商店（`reachableCounts`），这是「有没有退路」的量化。
- 训练数据来自公开 run 数据（Kaggle `Slay-the-Spire-data-master/runs` + `Slay_The_Spire_Stats-main`），`preprocess.py` 自己重建地图
  （`map_generator.py` 复刻地图生成）再打 label；模型文件 `mod/resources/route_model.json` 1.6 MB 随 mod 分发。

## 11. 第五版：工坊内自足的跑图驱动（v5，用户 m10695 定稿方向）

> 本版取代 §4f.1 的分发讨论作为**实施方案**：目标形态固定为「单 jar、订阅即用、全部计算在游戏进程内」，
> LLM 与外部进程都不是必需项。§1–§10 的技术结论（? 精算、真引擎测掉血、beam、硬安全、各屏处理、存档隔离）全部保留。

### 11.1 硬约束（工坊形态决定的技术边界）

| 约束 | 要求 | 为什么 |
|---|---|---|
| 依赖 | 只依赖 ModTheSpire + BaseMod | 订阅者必装；多一个依赖就多一层装不上的风险 |
| 进程 | 不起外部进程、不带 exe、不带 Python | 工坊包只能是 jar + 资源；外部进程是「能用」的最大敌人 |
| 网络 | 默认**零网络** | 隐私 + 审核 + 断网可用；LLM 若用只能可选、失败即降级 |
| 写盘 | 只写 mod 自己的配置与日志；存档隔离沿用 B25/PlayerPrefs | 玩家存档不可被碰（已出过事故） |
| 卡帧 | 单帧计算预算 ≤ 8 ms，超了切下一帧 | 不能像早期 F8 那样冻结游戏（B13/P2-9 教训） |
| 可复现 | 同 seed + 同状态 → 同决策（决策可重放） | 玩家要能相信「它每次都这么选」 |

### 11.2 为什么这一版「不笨」：四层账，越往下越贵越准

**L1 精确静态账（微秒级，全部来自游戏自己的公式）**
- ? 房间：`new Random(Settings.seed, eventRng.counter)` + `EventHelper.roll` 精确算出下一个 ? 是什么（§3.4）；relic 修正（Juzu/Tiny Chest/Deadly Events）自动生效。
- 金币：普通 10–20、精英 25–35、Boss 100±5，A13+ ×0.75（§3.3）。
- 营火回血 0.3×maxHP（Regal Pillow +15）；删牌 75 起每次 +25；牌价 50/75/150 × 0.9–1.1。
- 精英/Boss 的遗物清单、三把钥匙（红=Recall、绿=`hasEmeraldKey` 可读、蓝=宝箱）、Act 4 门槛。
- 输出：每个候选房间的「期望 HP 变动」——这一层已经比「数前面有几个营火」聪明得多。

**L2 真引擎测关键战斗（百毫秒级，本 mod 独有）**
- 只测影响决策的几场：本幕 Boss（必测）、候选路线上的精英（测）、第 3 场以后的普通怪（抽测 1 场）。不做全图穷举。
- 预算：普通怪 400 ms、精英 800 ms、Boss 1500 ms；拿不到胜线就按「最坏线掉血 + 标记高风险」，不当成 0。
- 缓存键 = 牌组指纹 + 遭遇 + 进阶 + HP 档（§3.5），同一幕内重复路线直接复用。
- 一次完整评估 3–8 场 ≈ **2–6 秒**，正好是玩家看地图的时间。

**L3 beam + 硬安全 + 可解释（毫秒级）**
- Beam 宽度 6，每节点 3 个候选，逐层累加 `gamma^(i-1) × 折算 HP`（gamma=0.9）。
- 安全做成**硬过滤**不是加分：HP<50% 禁选精英、连续 3 战无营火禁选精英、弱牌组+低 HP+精英直接丢弃。
- 每个候选显示分项：`预计 -7 HP（战斗实测 3 场）· 营火 +12 · 商店值 4 金/血` —— 玩家能反驳。

**L4 可选先验（默认关）**
- 内置小权重表（社区路线经验，几十行）只用于平局 tie-break；默认权重 0，A/B 证明更好才开。
- 不内置 route-plan 的 LightGBM 模型（无 LICENSE，且 label 是「专家下一步」）。要做就别做成 `Prior` 接口，自己用公开数据重训。

### 11.3 分帧与「不让玩家等」

关键机会：**地图界面是游戏的静止状态**（`DungeonMapScreen` 打开时战斗/动画都不跑），最适合算路。

| 时刻 | 动作 | 玩家感知 |
|---|---|---|
| 打开地图第 1 帧 | 立刻用 L1 静态账给出 Top-3（<10 ms） | 马上有推荐，可以先点 |
| 之后每帧 ≤8 ms | 逐场补测 L2，边算边更新排名与数字 | 从「估算」变成「实测」，进度条显示「已测 2/5 场」 |
| 3 s 到时 | 用当前最好结果定稿；按钮「再精算 20 s」可继续 | 不强制等待 |
| 玩家已选点 | 立刻停止，不留后台任务 | 不抢 CPU |

实现：复用 `Solver.PortfolioSession` 的分帧模式（P2-9 已验证），新增 `RouteSession`，每帧 `advance(budgetNanos)`。

### 11.4 选牌 / 事件也要「不笨」

| 决策 | 做法 | 成本 |
|---|---|---|
| 三选一 | L1 静态影响分（真实数值差：`makeCopy().upgrade()`）+ 对**最可能的下一个精英/Boss** 跑 A/B（两张候选各 300 ms），数值差与实测差加权 | 0.6–1 s |
| 跳过奖励 | 算「本幕剩余牌位需求」与牌组稀释惩罚（≥15 张后每张 0.5 HP） | 0 ms |
| 事件 | 内置原版事件表（约 50 条，写「每个选项实际做了什么」）+ 沙箱试跑 diff 校正；mod 事件自动走 diff（0.3–1 s） | 0.3–1 s |
| 商店 | 按剩余金币与「下一场精英/Boss 缺什么」排序（不是固定优先级） | 0 ms |
| 营火 | 血量 <55% 休息，否则按缺升级数锻造；红钥匙条件明确显示 | 0 ms |

全部离线，无 LLM。装了 LLM 才用于「事件原文的语义判断」，失败直接走内置表。

### 11.5 驾驶（自动跑）用状态机，逐屏接管

`run/Driver` 每帧看当前屏 → 对应 handler → 调游戏自己的接口（不重写流程）：

| 屏 | handler | 行为 |
|---|---|---|
| 地图 | `MapHandler` | 用 RouteSession 的 Top-1 点节点 |
| 战斗 | 现有 `Solver` | 自动出牌 / 深度搜索 |
| 战后奖励 | `RewardHandler` | §11.4 选牌 / 取金币 / 药水 / 遗物 |
| 事件 | `EventHandler` | 表 + diff（可选 LLM） |
| 营火 | `CampfireHandler` | 休息 / 锻造 / Recall |
| 商店 | `ShopHandler` | 按缺口买 |
| 宝箱 | `TreasureHandler` | 蓝钥匙决策 |
| Boss 遗物 | `BossRelicHandler` | 按牌组强弱选 |
| 幕间 | `TransitionHandler` | 三钥匙齐进 Act 4 / 下一幕 |

**默认「半自动」**：面板给建议 + 倒计时 2 s 自动点（玩家可随时接管）；「全自动」是开关。半自动更容易被信任，也让 bug 不至于毁掉一局。

### 11.8 验收（怎么证明「不笨」且「能订阅」）

1. **同 seed 双跑一致**：同一 seed 跑两次，路线/选牌/事件决策逐条相同（可重放日志）。
2. **可解释**：面板每个候选能展开分项（实测掉血、静态账、安全过滤原因）。
3. **不掉帧**：整幕评估期间平均帧时间 < 16 ms，单帧计算 < 8 ms（可做门禁）。
4. **对比 route-plan**：同 seed、同角色、同进阶各跑一局，比「到 Boss 时剩余 HP / 死亡楼层 / 是否通关」，至少 5 个 seed 做表。
5. **订阅可用性**：干净环境（只装 MTS+BaseMod）订阅 → 开一局 → 全程无报错、无外部依赖。

### 11.10 输出形态：先给「下一步」，不是先给整幕长路线（v5.1，用户 m10713 第 3 条）

玩家可能自己走一半再把控制权交回来，所以**主输出必须是当前节点 => 下一层走哪个**；整幕路线只是副产品。

```
当前节点：第 7 层 · 普通怪房
  左  普通怪        预计 -3 HP（实测）   之后两步到营火 +12   综合 +9   <- 推荐
  中  ?（第 2 个）   实为事件（已算出）   预计 -1 HP           综合 +5
  右  精英           HP 58% 高风险       预计 -14 HP / 遗物   综合 -4   （不建议：血量低于 50% 不打精英）
  建议走左        [执行] [看理由] [再精算 20s]
```

- 每个候选固定三样：**一句话理由 + 一个折算成 HP 的数 + 2 步预览**；「看理由」展开三项分项（战斗/房间/风险）。
- 计算顺序（对应 §11.3）：第 1 帧用 L1 静态账把 3 个候选排出来 => 之后每帧 ≤8 ms 只精算 Top-2 => 3 s 定稿。
- 玩家中途接管：任何时刻打开地图都**从当前节点重算**，不需要知道前面怎么走的；缓存键含当前牌组/HP 档，所以重算通常命中缓存、几十毫秒出结果。
- 事件屏同格式：`选 1：拿 99 金，失去 3 最大生命（净 -0.4 HP）` / `选 2：删一张牌`；点开看依据（事件表条目 or 试跑 diff）。
- 选牌屏同格式：`拿 治疗术：对下一个精英 -1.5 HP（A/B 实测）` / `跳过：省 1 次删牌位`。
- 与 route-plan 的关键区别：它的输出是「整条路线的 3 个高亮」，路线一变就得整条重算；我们的输出是「当前这一步」，天然支持中途接手。

实现落点（P5-3）：`NextOptions` 枚举 `currMapNode.getEdges()`，每个候选跑一次 beam 续算得到 best continuation 价值，Top-2 再做 L2 精算；面板 = `ui/MapOverlay` 三行。
